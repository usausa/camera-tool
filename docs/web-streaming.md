# 🌐 Web 配信

WebStream(`src/CameraTool.WebStream`)は、カメラ映像を ASP.NET Core からブラウザーへ配信するサーバー。

- `http://localhost:5080` で待ち受ける。ブラウザーで開くとビューアーが出る
- ⚠️ ローカル専用で認証はない
- ⚠️ FaceViewer とはカメラを同時に使えない(どちらも排他で開く)
- パスとメッセージの形式は [Web API](web-api.md)、H.264 は [H.264 配信](h264-streaming.md)、設定は [使い方](usage.md)

## 🔄 処理の流れ

```
FrameArrived (取込スレッド)
  ├─ JPEG のクライアントがいれば、フルレンジの NV12 を WIC で JPEG 化(平面 YCbCr のまま渡す)
  │    ・MJPG 由来の NV12: カメラのバッファをそのまま渡す
  │    ・YUY2: フルレンジの NV12 に変換してから渡す
  │  → プールしたバッファに、ヘッダー(最新の検知結果)と JPEG を書き、FrameHub に公開(最新の1枚だけを持つ)
  │             ↓
  │  接続ごとの送信ループ: 新しいフレームを待って送信(送信中に届いたフレームは飛ばす)
  │
  ├─ H.264 のクライアントがいれば H.264 に圧縮して、別の FrameHub に公開(H.264 配信を参照)
  │
  ├─ エンコードの後、検知範囲の中で動体検知 → 結果は次のフレームのヘッダーに入る
  │
  ├─ 検出器が空いていれば 320x240 のテンソルを作る(連動時は、動きがない間は間隔を空ける)
  │             ↓
  │  検出スレッド: ONNX Runtime で推論 → 範囲外の顔を除き、結果は次のフレームのヘッダーに入る
  │
  └─ 物体検知: 前回から Interval が過ぎていれば 640x640 のテンソルを作る(連動は顔検出と共通)
                ↓
     検出スレッド: D-FINE-N で推論(約 100 ms)→ 範囲外の物体を除き、結果は次のフレームのヘッダーに入る
```

- 1フレームを1回だけエンコードし、全クライアントに同じバッファを送る。バッファは参照カウントで管理し、全員が送り終えたらプールに戻す
- 待ち合わせは使い回す `IValueTaskSource`。フレームごとに Task を作らない
- クライアントがいないときは、変換もエンコードも検知もしない
- 検知は配信の後に処理するので、配信は遅れない。そのかわり、枠やマスは1フレーム前の結果

## 📏 指標

| 指標 | 内容 |
|:--|:--|
| 到着→配信可能 | FrameArrived から FrameHub に公開するまで(変換・エンコードを含む) |
| 配信可能→送信開始 / 送信完了 | 公開から、各クライアントへの送信を始めるまで / OS に渡し終えるまで |
| 配信可能→受信 | 公開から、クライアントがメッセージ全体を受け取るまで |
| 受信 / 描画 | カメラのタイムスタンプから、クライアントが受け取るまで / canvas に描くまで |

## 📊 Phase W1(最初の実装)

- 構成: WinRT の `BitmapEncoder`(WIC)で BGRA から JPEG(品質80)へ。バッファはフレームごとに確保。GC は ASP.NET Core 既定の Server GC
- 方法: クライアント1台で約30秒。受信側はヘッドレスの WebSocket クライアント(.NET)と組み込みブラウザー(Chromium)。GC とメモリは dotnet-counters

|:--|--:|--:|--:|--:|--:|--:|--:|
| YUY2 640x480 | 0.13 ms | 1.6 / 5.0 ms | 1.9 / 5.2 ms | 59 KB | 14.5 Mbps | 0.36 % | 2.3 MB/s |
| NV12 1280x720 | 0.32 ms | 3.5 / 4.5 ms | 3.9 / 5.0 ms | 142 KB | 34.9 Mbps | 0.65 % | 4.9 MB/s |
| NV12 1920x1080 | 0.75 ms | 6.8 / 8.7 ms | 7.6 / 9.8 ms | 269 KB | 65.3 Mbps | 1.19 % | 8.6 MB/s |

| 構成 | GC(gen0 / gen1 / gen2) | GC の停止時間 | ワーキングセットの最大 |
|:--|--:|--:|--:|
| YUY2 640x480 | 1 / 0 / 1 | 5.3 ms | 約1.3 GB(90秒間) |

どの構成も約30fpsで取りこぼしなし。MJPEG も同様(curl で3秒間に89フレーム)。

### 💡 分かったこと

- **サーバー内の遅延はほぼエンコードの時間**: 到着→配信可能は 1.9 / 3.9 / 7.6 ms(480p / 720p / 1080p)。大半が WIC のエンコードで、AVX2 の変換は 0.13〜0.75 ms
- **ローカルでの送信は速い**: 配信可能→受信は 480p・720p で 0.2〜0.4 ms。1080p(約270 KB/フレーム)は中央値 0.6 ms だが、ときどき 20 ms 前後遅れる
- **取込→描画の大半はカメラ側**: カメラ(約34〜40 ms)+ サーバー(2〜8 ms)+ ブラウザーのデコード(1.7〜6.6 ms)
- **WinRT の `BitmapEncoder` はネイティブのメモリを GC まで手放さない**: GC ヒープは約30 MB なのに、ワーキングセットが1フレーム約1.4 MB ずつ増え、GC(ファイナライザー)のときだけ減る。Server GC は間隔が長く、480p でも最大約1.3 GB(Workstation GC では約370 MB)
- **720p 以上は JPEG のバッファ(85 KB 超)が LOH に入り、gen2 GC が3〜4秒に1回**: 停止時間は合計 10 ms 程度だが、割当は 4.9〜8.6 MB/s
- エンコーダーとバッファは Phase W2 で改善した

## 📊 Phase W2(チューニング)

変更点

- 🎨 **エンコーダー**: WIC を COM の vtable で直接呼ぶ `JpegEncoder`(Vision)に置き換え。NV12 を平面 YCbCr(8bppY + 16bppCbCr)のまま渡すので色変換がなく、結果はプールしたバッファへ直接書く。WIC のオブジェクトはフレームごとにその場で解放
- 📥 **入力**: MJPG 由来の NV12(フルレンジ)はコピーせずに渡す。YUY2 は `ImageConverter.Yuy2ToNv12`(SSSE3)でフルレンジの NV12 に。リミテッドレンジの NV12 は `Nv12ToFullRange` で広げる
- 🧵 **スレッド**: トリプルバッファとエンコードのループをやめ、取込スレッドでそのままエンコードして公開
- ♻️ **バッファと待ち合わせ**: 参照カウントとプール、使い回す `IValueTaskSource`(上の「処理の流れ」)

JPEG エンコーダーの比較(カメラの1フレーム、品質80、1回あたり)

| 解像度 | WinRT BitmapEncoder(BGRA) | WIC 直接(BGR24) | WIC 直接(平面 NV12) |
|:--|--:|--:|--:|
| 640x480 | 1.38 ms / 79 KB 割当 / 35.03 dB | 1.00 ms(+BGR24 への変換 0.35 ms) | **0.86 ms** / 35.07 dB |
| 1280x720 | 3.95 ms / 177 KB / 36.22 dB | 2.71 ms(+1.09 ms) | **2.24 ms** / 36.29 dB |
| 1920x1080 | 8.53 ms / 327 KB / 37.33 dB | 5.43 ms(+2.48 ms) | **4.31 ms** / 37.36 dB |

- dB は元の画像との PSNR
- WIC の JPEG エンコーダーは BGRA を受け付けず、24bppBGR への変換が要る
- 平面 NV12 が最速で、色変換が1回減るぶん画質もわずかに良い。こちらだけを使う(設定での切り替えはない)

サーバー側(クライアント1台、W1 → W2、平均)

| フォーマット | 変換 | エンコード | 到着→配信可能 | CPU | Allocated | gen2 GC(29秒) | ワーキングセット |
|:--|--:|--:|--:|--:|--:|--:|--:|
| YUY2 640x480 | 0.13 → 0.07 ms | 1.6 → 0.77 ms | 1.9 → 0.93 ms | 0.36 → 0.26 % | 2.3 MB/s → 43 KB/s | 1 → 0 | 1.3 GB → 107 MB |
| NV12 1280x720 | 0.32 → 0 ms | 3.5 → 2.0 ms | 3.9 → 2.1 ms | 0.65 → 0.41 % | 4.9 MB/s → 65 KB/s | 8 → 0 | 649 MB → 108 MB |
| NV12 1920x1080 | 0.75 → 0 ms | 6.8 → 4.2 ms | 7.6 → 4.3 ms | 1.19 → 0.78 % | 8.6 MB/s → 100 KB/s | 9 → 0 | 1.3 GB → 109 MB |

- Allocated は dotnet-counters の計測セッションの分も含む
- 90秒続けても、ワーキングセットは 106〜111 MB で一定。GC は gen1・gen2 が1回ずつ(停止時間は合計 6.8 ms)

| 構成 | 各クライアント | 配信可能→受信 | CPU |
|:--|:--|--:|--:|
| 1280x720 × 4台 | 29.8 fps、取りこぼしなし | 0.50 ms | 0.68 %(1台では 0.41 %) |

### 💡 分かったこと

- **WIC は COM で直接呼び、平面 NV12 で渡すのが最速**: WinRT 経由より 1.6〜2倍速く、GC の割当もない。MJPG 由来の NV12 は変換もいらない
- **サーバー内の遅延は約半分**: 到着→配信可能は 0.9 / 2.1 / 4.3 ms(480p / 720p / 1080p)。ほぼエンコードの時間で、キューやスレッド切り替えの待ちはない
- **メモリは一定**: ワーキングセットは約110 MB のまま、定常状態で gen2 GC は起きない。配信経路のコードはフレームごとの割当がない(割当トレースで確認)。残りの 40〜100 KB/s は WinRT のイベント引数(約0.5 KB/フレーム、後でなくした)と ManagedWebSocket・Kestrel の内部
- **1080p の遅れの原因は受信側の TCP**: サーバーは配信可能から約0.7 ms で送り終えているが、受信側のソケットのバッファが既定だと、約290 KB のメッセージで 10〜25 ms の遅れが約2割のフレームに出る。.NET のクライアントで受信バッファを 4 MB にすると消えた(0.66 ms)。ブラウザー(Chromium)でも 1080p で平均 6〜11 ms(最大 約40 ms)遅れ、サーバーからは変えられない。遅延を最小にするなら、解像度や品質を下げてフレームを小さくする
- **ブラウザーまでの遅延の大半は、引き続きカメラ側**(約34〜40 ms)。720p ではサーバーの改善分(約2 ms)がそのまま描画までの遅延に出た
- **複数クライアント**: エンコードは1回のまま。720p で1台増えるごとの CPU の増加は約0.1 %(全コア比)

## 📊 Phase W3(顔検出)

構成は W2 と同じで、`Detect:Enable` を切り替えて比べた(クライアント1台、約30秒、平均)。

| 構成 | 検出 fps | 前処理 | 推論 | 到着→配信可能 | 受信(.NET) | 配信可能→受信 | CPU | Allocated | ワーキングセット |
|:--|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| YUY2 640x480 検出なし | − | − | − | 0.87 ms | 35.1 ms | 0.25 ms | 0.21 % | 45 KB/s | 144 MB |
| YUY2 640x480 検出あり | 30.3 | 0.77 ms | 7.28 ms | 0.84 ms | 35.1 ms | 0.24 ms | 1.23 % | 46 KB/s | 146 MB |
| NV12 1280x720 検出なし | − | − | − | 1.83 ms | 39.4 ms | 0.38 ms | 0.37 % | 83 KB/s | 145 MB |
| NV12 1280x720 検出あり | 30.0 | 0.78 ms | 7.14 ms | 1.81 ms | 39.5 ms | 0.39 ms | 1.35 % | 69 KB/s | 148 MB |

ブラウザーでは顔枠と信頼度が映像に重なり、検出の遅れ(フレームの連番 − 検出したフレームの連番)は1フレームだった。

### 💡 分かったこと

- **顔検出は配信の遅延に影響しない**: 到着→配信可能も受信までの遅延も、差は誤差の範囲。前処理はエンコードの後に取込スレッドで行い(約0.8 ms)、推論は専用のスレッド
- **増えるのは CPU だけ**: 推論 約7.2 ms × 30fps で、1コアの約24 %(全コア比で約1 %)。割当はほぼ増えない(推論1回あたり約21バイト)
- **顔枠は1フレーム遅れる**: 公開する時点では、まだそのフレームの推論が終わっていない。検出を待つと配信が推論の時間(約8 ms)だけ遅れるので、遅延の小さいほうを選んだ
- **ワーキングセットは約35 MB 増える**: ONNX Runtime とモデルを起動時に読むため(画面から ON/OFF できるよう、OFF でも読んでいる)
