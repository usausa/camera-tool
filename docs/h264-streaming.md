# 🎞️ H.264 配信

ビューアーの表示方式「WebSocket (H.264)」。サーバーが Media Foundation の H.264 エンコーダーで圧縮して `/ws-h264` から送り、ブラウザーは WebCodecs の `VideoDecoder` でデコードして canvas に描く。

- ヘッダーは `/ws` と同じなので、重ね描きと検知範囲の編集もそのまま使える
- JPEG と MJPEG も残している(既定は JPEG)
- ⚠️ WebCodecs は secure context(localhost か HTTPS)でだけ使える

## ⚖️ 方式の比較

| 方式 | 長所 | 短所 |
|:--|:--|:--|
| WebSocket + JPEG | 実装が簡単。フレームが独立していて、飛ばしても次から表示できる | ビットレートが高い(480p で約 14 Mbps、1080p で約 70 Mbps) |
| ✅ WebSocket + H.264 + WebCodecs(採用) | ビットレートが約 1/4。ヘッダーと送信の仕組みをそのまま使える。ブラウザーはハードウェアでデコード | 前のフレームに依存するので、飛ばしたらキーフレームまで待つ |
| WebRTC(SIPSorcery など) | 輻輳制御・再送・NAT 越えがある。ブラウザーの標準の仕組みで再生できる | シグナリングと ICE / DTLS / SRTP が要る。ジッタバッファで遅延が増えやすい。重ね描きのデータはデータチャネルで送って同期させる。エンコーダーは別に要る。SIPSorcery のライセンスに用途の追加条項がある |

- 同じ PC か LAN の中で見るもので、外からの閲覧はしない。NAT 越えや輻輳制御は不要なので、WebRTC は使わない
- WebRTCme は .NET MAUI / Blazor のクライアント向けで、サーバーから自前のフレームを送る用途に合わない

## 🧪 エンコーダーの試作

先にスクラッチの試作で、Media Foundation の H.264 エンコーダーをカメラの映像で測った(CBR、低遅延モード、Main プロファイル、キーフレーム 60 フレームごと)。

| エンコーダー | 解像度 | ビットレート | エンコード | PSNR(RGB) |
|:--|:--|--:|--:|--:|
| NVIDIA H.264 Encoder MFT(NVENC) | 640x480 | 2 / 4 Mbps | 1.77 / 1.48 ms | 35.83 / 37.03 dB |
| 〃 | 1280x720 | 4 / 8 Mbps | 2.18 / 1.69 ms | 34.69 / 35.79 dB |
| 〃 | 1920x1080 | 8 / 16 Mbps | 3.47 / 3.46 ms | 34.49 / 35.38 dB |
| H264 Encoder MFT(Windows 標準、ソフトウェア) | 640x480 / 1280x720 / 1920x1080 | − | 1.05 / 2.06 / 3.31 ms(1コアの 12 / 37 / 87 %) | − |
| JPEG(品質80、参考) | 640x480 / 1280x720 / 1920x1080 | 14.5 / 34.9 / 65.3 Mbps | 0.77 / 2.0 / 4.2 ms | 35.07 / 36.29 / 37.36 dB |

- NVENC は非同期の MFT。普通のメモリーの NV12 をそのまま受け取れる(D3D のデバイスは不要)。CPU の増加は1コアの数 %
- どちらも1入力ごとに1出力。要求したキーフレームは次のフレームで出る。キーフレームには毎回 SPS / PPS が付く(Annex B)
- 画質は 480p 4 Mbps で JPEG より高く、720p 8 Mbps・1080p 16 Mbps で JPEG より 0.5〜2 dB 低い程度。この値を `H264:Bitrate` の自動の値にした
- Microsoft AVC DX12 Encoder は、D3D12 のデバイスがないと出力の型を設定できない(0x80041000)ので使わない

## 🔄 処理の流れ

```
FrameArrived (取込スレッド)
  ├─ JPEG のクライアントがいれば JPEG 化(従来どおり)
  ├─ H.264 のクライアントがいれば、NV12 をエンコーダーの入力サンプルにコピー(範囲はカメラのまま)
  │    ・NV12: カメラのバッファからコピー
  │    ・YUY2: NV12 に並べ替えてからコピー
  │             ↓
  │  エンコーダーのスレッド: NVENC(非同期、イベントを待つ)/ ソフトウェア(同期)で圧縮
  │    → 出力のコールバックで、ヘッダー(最新の検知結果 + キーフレームのフラグ)と H.264 を書き、H.264 用の FrameHub に公開
  │             ↓
  │  接続ごとの送信ループ: 接続直後と、フレームを飛ばした後は、次のキーフレームまで送らない
  │
  └─ 動体検知・顔検出・物体検知(JPEG か H.264 のどちらかにクライアントがいれば動く)
```

- 🧩 **エンコーダー**(Vision の `H264Encoder`): Media Foundation を COM の vtable で直接呼ぶ。ハードウェアを先に試し、設定できた最初のものを使う(なければ Windows 標準のソフトウェア)。設定は低遅延モード、CBR、キーフレームの間隔、B フレームなし、Main プロファイル
- ⏱️ **作成と解放**: 最初のクライアントが来たときにバックグラウンドで作る(NVENC は 0.6〜0.8 秒、ソフトウェアは約 45 ms)。フレームの大きさか範囲が変わったら作り直し、クライアントがいない状態が 10 秒続いたら解放する
- ♻️ **入力**: サンプルは4つをプールし、エンコーダーが参照を手放したものだけを使い回す。エンコーダーが処理中に次のフレームが来たら、待っている古い方を新しい方で置き換える(状態の `h264DropFps` で数える)
- 🔗 **フレームの対応**: 入力のサンプルの時刻に取込時刻を入れ、出力の時刻から元のフレーム(連番・到着時刻)を引く。出力はプールしたバッファに1回コピーして公開する。フレームごとのマネージドの割当はない
- 🔑 **キーフレーム**: 接続直後と、送信が遅れてフレームを飛ばした後は、次のキーフレームまで待ち、エンコーダーに要求する(500 ms に1回まで)。ブラウザーもデコーダーのエラーやキューのあふれのときに、テキストのメッセージで要求する
- 🌐 **ブラウザー**: キーフレームの SPS からコーデック文字列(`avc1.4D401E` など)を作って `VideoDecoder` を設定する(`optimizeForLatency`、`prefer-hardware`、description なしの Annex B)。出てきた `VideoFrame` を canvas に描き、範囲・動き・物体・顔を重ねる。デコーダーのキューが3つを超えたら、次のキーフレームまで捨てる

## 🎨 色(範囲とマトリックス)

- ❌ **最初の失敗**: JPEG と同じフルレンジの NV12 を渡し、範囲だけを指定した。canvas で比べると輝度の標準偏差が JPEG の 1.16 倍(≒255/219)で、コントラストが強すぎた。SPS の VUI に `video_full_range_flag=1` は入っていたが、colour description(原色・伝達関数・マトリックス)がないため、Chrome はビデオレンジの BT.709 として扱っていた(`VideoFrame.colorSpace` の `fullRange` が false)
- ✅ **NVENC**: メディアタイプに `MF_MT_YUV_MATRIX`(BT.601)と `MF_MT_VIDEO_PRIMARIES` / `MF_MT_TRANSFER_FUNCTION`(BT.709)を付けると colour description を書き、Chrome は範囲と BT.601 を正しく扱った
- ⚠️ **sRGB の伝達関数は使えない**: `MFVideoTransFunc_sRGB` は NVENC が対応しておらず、伝達関数が 0 になって Chrome は colour description 全体を無視した
- ⚠️ **ソフトウェアのエンコーダー**: 範囲のフラグしか書かない。そこで、どのエンコーダーでもコントラストが合うよう、H.264 にはカメラの範囲のまま渡す。YUY2 はビデオレンジのまま並べ替えるだけ、MJPG 由来の NV12(720p / 1080p)はフルレンジのまま送る
- 🔍 **確認**: 同じ連番のフレームを `/ws` と `/ws-h264` から受け取ってデコードし、画素ごとに比べた(33〜39 フレーム)

| エンコーダー | RGB の平均の差 | 輝度の標準偏差(H.264 / JPEG) | PSNR(2つのデコード結果) |
|:--|--:|--:|--:|
| NVENC | 0.2 以下 | 73.48 / 73.46 | 34.7 dB |
| ソフトウェア | 0.5 以下 | 73.27 / 73.48 | 34.1 dB |

ソフトウェアのエンコーダーは BT.709 のマトリックスとして扱われる。この映像では差は小さいが、色の濃いものほど差が出る。

- どの構成も約 30 fps で、取りこぼしも、エンコーダーが捨てたフレームもない。キーフレームは 2 秒ごと(30 秒で 15 枚)

🔑 キーフレームと回復

- 途中から接続したクライアントも含め、全員が最初にキーフレームを受け取った
- 60 フレームごとに 1.5 秒読むのを止めるクライアント(受信バッファ 16 KB): サーバーでの飛びが4回起き、4回ともキーフレームから再開。止まっている間も、ほかのクライアントへの配信は続いた
- ブラウザーからの要求(テキストのメッセージ)は、5回とも次のフレームがキーフレームになった

## 💡 分かったこと

- **ビットレートは JPEG の約 1/4**: 14.5 → 4.0 Mbps(480p)、35.0 → 8.0 Mbps(720p)、68.3 → 16.0 Mbps(1080p)。1080p では、JPEG の大きなフレーム(約 280〜340 KB)で起きていた受信側の TCP の遅れ(95%点 16 ms)がなくなった
- **取込→描画は 720p 以上で H.264 のほうが短い**: エンコードは JPEG より 1.5〜2 ms 長いが、ブラウザーのデコードは 0.4〜0.5 ms(JPEG は 1.7〜7.2 ms)。差は 480p で +0.7 ms、720p で −1.4 ms、1080p で −6.9 ms。最大値も 1080p で約 25 ms 小さい
- **サーバーの CPU は減る**: NVENC では CPU に残るのは入力のコピーだけ。720p で JPEG の半分、1080p で約 1/3。ソフトウェアのエンコーダーは 1080p で1コアの約 75 %
- **NVENC の時間は GPU の電源状態で変わる**: エンコードだけでは負荷が軽く、GPU は数秒ごとに P0(ビデオのクロック 2070 MHz)と P5 / P8(1470 / 1185 MHz)を行き来する。480p で約 0.9〜3 ms、1080p で約 4〜6.5 ms とばらつく。ブラウザーの描画などで GPU が動いているときは短い。ソフトウェアのほうが速いこともある(480p 1.5 ms、1080p 3.6 ms)が、CPU を多く使う
- **色はカメラの範囲のまま渡し、範囲とマトリックスを明示する**: 範囲のフラグだけでは、Chrome は colour description がないとビデオレンジの BT.709 として扱う。NVENC はメディアタイプの色の属性を VUI に書くが、ソフトウェアは範囲しか書かない
- **途中参加と取りこぼしはキーフレームで回復できる**: 要求は次のフレームで反映されるので、待ちは1〜2フレーム(要求は 500 ms に1回までなので、続けて飛ぶと最大 500 ms 待つ)
- **メモリ**: ワーキングセットは約 50 MB 増える(Media Foundation と NVENC のドライバー)。フレームごとの割当はなく、Allocated は JPEG と同じ程度。NVENC の作成は約 0.7 秒かかるので、最初のクライアントで作り、10 秒使わなければ解放する
- **ローカルでは WebRTC はいらない**: WebSocket + WebCodecs で、JPEG と同じ遅延(1080p では短い)と約 1/4 のビットレートになった
