# 📦 物体検知

人・動物・乗り物などを、枠とクラス名で表示する(録画や通知はしない)。既定はオフ。画面の「Object detection」か `PUT /api/objects` でオンにする。モデルは最初にオンにしたときに読む(約 0.3 秒)。

## 🧠 モデル

Apache-2.0 の3つの候補をこの PC で比べて選んだ(Ultralytics の YOLO は AGPL-3.0 なので対象外)。

| モデル | 推論(1 / 2 スレッド) | 人を見つけた枚数 | 人の最高スコアの平均 |
|:--|--:|--:|--:|
| YOLOX-Nano(416x416) | 15.4 / 9.7 ms | 30 / 60 | 0.50 |
| YOLOX-Tiny(416x416) | 59.4 / 33.9 ms | 6 / 60 | 0.34 |
| D-FINE-N(640x640) | 102.8 / 71.0 ms | 59 / 60 | 0.61 |

- 推論時間は合成画像で 50 回の平均。人の検出は、WebStream のスナップショット 60 枚(0.5 秒おき、机の前に人がいる場面)で比べた(画像は保存も表示もせず、集計値だけを見た)
- YOLOX はカメラに近くて体が見切れている人をあまり見つけられない。D-FINE-N はほぼ毎回見つけるが重いので、間隔を空けて使う
- D-FINE-N は DETR 系で NMS がいらない。300 個のクエリーごとに対象クラスの中で最もスコアの高いクラスを選び、しきい値以上を残す
- 入力は RGB を 0〜1 にして 640x640 に引き伸ばしたもの。出力は 80 クラスのロジットと、0〜1 の中心・幅・高さ

## 🔄 処理の流れ

```
FrameArrived (取込スレッド、動体検知と顔検出の後)
  └─ オンで、検出器が空いていて、前回から Interval(200 ms)が過ぎていれば
     (連動時は、範囲内に動きがない間は IdleInterval ごと)
       640x640 に縮小 + RGB 化 + x / 255 でテンソルへ(前処理、AVX2)
                ↓
       検出スレッド: D-FINE-N で推論 → しきい値と対象クラスで絞る → 範囲外の物体を除く → 枠を表示 / ヘッダーに入れる
```

- 顔検出と同じ作りで、別のスレッドで動く。推論が取込・表示・配信を待たせない
- 入出力は IoBinding で事前に確保したバッファに結ぶので、推論ごとの割当はない
- 前処理の変換は顔検出と共通で、正規化だけを変える(顔は (x - 127) / 128、物体は x / 255)
- 検知範囲は枠の中心で判定し、連動(「Detect only on motion」)は顔検出と共有する
- 枠の色はグループごと: 人は青、動物は黄、乗り物は紫、その他は白。WPF のラベルは、文字ごとに一度だけ描いた図形を使い回す

## 💡 分かったこと

- **推論は約 100 ms で、最大 5 fps でも1コアの約半分を使う**: CPU の増え方は「推論時間 × 検出回数」とほぼ同じ。`Interval` 200 ms でも実際は約 4.6 fps(前回の前処理から 200 ms 後に届いたフレームで始めるため)。`Interval` 0 だと約 8 fps で、1コア近くを使う
- **取込・表示・配信には影響しない**: 取込スレッドで動くのは前処理(約 1.2〜1.3 ms)だけで、推論は専用のスレッド
- **連動と検知範囲で大きく減らせる**: 範囲内に動きがなければ 1 fps。顔検出も 1 fps になるので、物体検知なしで常に顔検出する場合より CPU が少ない
- **WPF のラベルは、文字を描くたびに割当が出る**: 信頼度はほぼ毎回変わるので、毎回描くと約 +84 KB/s(1回の更新で約 18 KB)。文字ごとに一度だけ描いて凍結した図形を使い回すと、約 +24 KB/s に減った
- **1080p では推論が少し遅い**(約 107 ms): 取込と変換の負荷が増え、CPU を取り合うため
