# 🔧 追加の改善

後から加えた改善。最初の2つと割当の見直し(2回目)は、FaceViewer と WebStream の両方に効く。

## 📥 フレーム受信の割当をなくす

- FrameArrived を、CsWinRT の投影ではなく COM の vtable で購読する(`FrameArrivedSubscription`)。ComWrappers で作ったハンドラーを add_FrameArrived に渡し、受け取った IMediaFrameReader から直接フレームを読む
- 投影ではイベントのたびに引数のラッパーが作られ、約440 B/フレームの割当になっていた(プローブで計測。直接購読では割当なし)
- FaceViewer(検出なし)の割当: 118 → 102 KB/s(YUY2 640x480)、113 → 104 KB/s(NV12 1280x720)
- WebStream: 割当トレースから WinRT のイベント引数が消え、配信経路に残る割当は ASP.NET Core と .NET の内部だけになった

## ⚡ 検出の前処理の SIMD 化

- TensorConverter で、列ごとの座標を先に計算し、4隅の値をスカラーで集めてから AVX2 で8画素ずつ補間・色変換する
- この PC(Ryzen 9 5900X)では gather 命令が遅いので使わない
- 計算の順序はスカラー版と同じで、結果はビット単位で一致する(テストで確認)

| 構成 | 変更前 | 変更後 |
|:--|--:|--:|
| FaceViewer YUY2 640x480 | 0.93 ms | 0.27 ms |
| FaceViewer NV12 1280x720 | 0.91 ms | 0.29 ms |
| WebStream YUY2 640x480 | 0.77 ms | 0.25 ms |
| WebStream NV12 1280x720 | 0.78 ms | 0.38 ms |
| WebStream NV12 1920x1080 | − | 0.35 ms |

前処理は約1/3。減った時間は1フレーム約0.5 ms(1コアの約1.5 %)で、CPU 使用率の差は計測のばらつきに埋もれる程度。

## 🎞️ MJPEG の表示を1フレーム早める(WebStream)

- Chromium は `multipart/x-mixed-replace` の各パートを、次のパートのヘッダーを受け取った時点で表示する
- 以前は「境界 + ヘッダー(Content-Length)+ JPEG」の順に書いていたので、各フレームが次のフレームの到着まで表示されず、1フレーム分(30fps で約33 ms)遅れていた
- JPEG の直後に、境界と次のパートのヘッダーを書くように変えた
- ⚠️ パートに Content-Length は付かない(次の JPEG の大きさはまだ分からない)。Content-Length で区切るクライアントでは読めないので、境界か JPEG の SOI / EOI で区切る。VLC などのプレイヤーは境界で区切るはず(この PC には入っておらず未確認)

テスト用のサーバーから2枚を3秒間隔で送り、組み込みブラウザー(Chromium)で表示された時刻を比べた。

| 書き方 | 1枚目 | 2枚目 |
|:--|--:|--:|
| ヘッダー + JPEG(変更前) | 3.0 秒後(2枚目の到着時) | 計測した6秒間は表示されない |
| ヘッダー + JPEG + 境界 | 3.0 秒後 | 計測した6秒間は表示されない |
| ✅ JPEG + 境界 + 次のヘッダー(変更後) | 25 ms 後 | 3.0 秒後 |

- JPEG の直後に境界だけを書いても、Chromium では変わらない
- 変更後は、`<img>` を作ってから 31 ms で最初のフレームが表示され、3秒間に89フレーム(約30fps)が描かれた
- curl で受け取った3秒分(61フレーム)も、すべてのパートが JPEG の SOI から EOI までそろっていた

## ♻️ 割当の見直し(2回目)

割当のトレース(GC の AllocationTick とスタック)で残りの割当を洗い出し、アプリ側で減らせるものを直した。

- **FaceViewer: 更新の通知をウィンドウメッセージにする**: 映像と、顔・物体・動きの重ね描きの更新は、ほかのスレッドから UI スレッドへ通知する。Dispatcher への投稿は1回ごとに DispatcherOperation や Task などを作るので、メッセージ専用のウィンドウへの PostMessage に替えた(`UpdateRequest`)。続けて来た通知を1回にまとめるのは今までどおり
- **FaceViewer: 同期コンテキストを使い回す**: WPF は Dispatcher の操作やウィンドウメッセージのたびに同期コンテキストを作る。起動時に `BaseCompatibilityPreferences.ReuseDispatcherSynchronizationContextInstance` を設定した
- **検出スレッドは実行コンテキストを引き継がない**(両アプリ): ホストの実行コンテキストを引き継いでいたので、FaceViewer では投稿のたびに複製されていた。`Thread.UnsafeStart` で始める
- **CPU 時間は `Environment.CpuUsage` で取る**(両アプリ): 1秒ごとの `Process.GetCurrentProcess()` は毎回割り当てる
- **WebStream: WebSocket の送信に取り消しのトークンを渡さない**: 取り消しできるトークンを渡すと、.NET の WebSocket は送信ごとに遅い経路(非同期の待ちと登録)を通る。送信中に取り消されたときは接続を中断する。待っている間の取り消しは今までどおり正常に閉じる(サーバーの停止では 1001 を送る)

YUY2 640x480、Release、各約40秒。

| アプリ | 構成 | 変更前 | 変更後 |
|:--|:--|--:|--:|
| FaceViewer | 顔検出 + 動体検知 | 201 KB/s | 161 KB/s |
| FaceViewer | + 物体検知 | 226 KB/s | 215 KB/s |
| WebStream | JPEG 1台 | 約 13 KB/s | 約 10 KB/s |
| WebStream | H.264 1台 | 約 34 KB/s | 約 29 KB/s |
| WebStream | JPEG + H.264、検知すべて | 約 22 KB/s | 約 12 KB/s |

- FaceViewer はアプリの計測値(5秒ごと)の平均。WebStream は割当が少なく、トレースの標本(約100 KB ごと)からの目安
- 実際の部屋を写しているので、場面で ±20〜40 KB/s ほどばらつく。物体検知ありの差はこの範囲に入る。直した割当そのものは、トレースから消えたことを確かめた
- GC はどの構成でも 0 回。FaceViewer の表示は約30fps、表示遅延(到着→表示)は平均 0.35〜0.39 ms で変わらない
- 残りの主なもの: FaceViewer は計測値パネルの文字のレイアウト(1秒ごと。次の項目で減らした)、WPF の描画の内部、毎フレームの `WriteableBitmap.Lock`(後で調べ、そのままにした)。WebStream は H.264 の送信バッファの取り直し(.NET の WebSocket の内部。後で調べ、そのままにした)、1秒ごとの状態、開発時のログ

## 🔤 計測値パネルの文字(FaceViewer)

計測値パネルは1秒ごとに約15個の値を書き換える。割当のトレースと、パネルと同じように値を書き換える小さな WPF アプリ(プローブ)で調べて直した。

- **値の欄を `ValueText` で描く**: TextBlock は文字が変わるたびに行のレイアウトをやり直し、1つの値で約10 KB を割り当てる。`ValueText` は ASCII の字形の番号と送り幅をフォントごとに1回だけ表にして、1本の GlyphRun で描く(約1 KB)。折り返す Objects の行は TextBlock のまま
- **見た目は TextBlock と同じ**: 大きさとベースラインは TextBlock と同じで、ベースラインは TextBlock と同じく画素にそろえる(ガイドライン)。19種類の文字列を 96 / 144 DPI で描き比べると、ほとんどは画素まで一致し、違いは数画素の薄い濃淡だけ。アプリの各行の位置と大きさも変わらない。フォントの代替や字形の置き換えはしない(フォントがないときは FormattedText で描く)
- **平均と最大の組は自分で書式を付ける**: `LatencyValue` は `ISpanFormattable` で「平均 / 最大」を書く(`{0:F1} ms` → `34.1 / 48.4 ms`)。`CaptureLatency.Average` のように構造体の中までたどるバインドは、値が変わるたびに監視を付け直し、1行で約3.6 KB を割り当てていた

YUY2 640x480、Release。変更前と変更後を交互に各約40秒、2回ずつ測った平均。

| 構成 | 変更前 | 変更後 |
|:--|--:|--:|
| 顔検出 + 動体検知 | 203 KB/s | 85 KB/s |
| + 物体検知 | 256 KB/s | 83 KB/s |

- 変更前は上の表の変更後より多い。平均と最大を構造体にまとめたときに構造体の中までたどるバインドが増えていた分(約30 KB/s)と、場面のばらつき
- 物体検知ありの変更後は 111 と 55 KB/s で、場面で大きく変わる
- トレースから TextBlock の文字のレイアウトがなくなった。残りは WPF の描画の内部(フレームごとの Dispatcher の操作など)と重ね描き
- GC は 0 回。表示遅延(到着→表示)は平均約 0.4 ms で変わらない

## 🖼️ 映像の更新の割当(FaceViewer、変更なし)

映像はフレームごとに WriteableBitmap を Lock → コピー → AddDirtyRect → Unlock する。プローブ(640x480、約30fps、画面外のウィンドウ)で1フレームの割当を比べ、今のままにした。

| 更新のしかた | 1フレームの割当 |
|:--|--:|
| ブラシの色を変えるだけ(WPF の描画の予約) | 約 920 B |
| ✅ WriteableBitmap(今のまま) | 約 980 B |
| InteropBitmap + Invalidate | 約 800 B |

- 大部分は、表示が変わったときに WPF が描画を予約する処理(Dispatcher の操作)で、どの表示の変更でもかかる
- WriteableBitmap 自身の分は約 60 B(Lock で取り直すハンドルなど、約2 KB/s)
- InteropBitmap なら約 180 B 減るが、二重バッファーがないので、描画中に次のフレームを書くと画像が乱れるおそれがある

## 📼 H.264 の入力を1回で書く(WebStream)

- YUY2 のフレームは、NV12 に並べ替えて自前のバッファに置き、それをエンコーダーの入力サンプルにコピーしていた(2回書く)
- `H264Encoder.EncodeYuy2` で、ロックした入力サンプルに直接並べ替える。範囲はカメラのまま。NV12 のフレームは今までどおりコピーするだけ
- 自前のバッファ(640x480 で約 450 KB)もなくなった。書く内容は同じ(同じフレームを両方の方法でソフトウェアのエンコーダーに通すと、出力が一致する。テストで確認)

| 構成 | 変更前 | 変更後 |
|:--|--:|--:|
| H.264 の入力(NVENC、YUY2 640x480) | 0.095 ms | 0.065 ms |

- Release、H.264 のクライアント1台で約30秒を2回、5秒ごとの平均。最大は 0.12〜0.29 ms → 0.08〜0.12 ms
- 1コアの 0.1 % 程度の差で、CPU 使用率には表れない。取込→受信の遅延も変わらない(約 36〜37 ms)

## 📤 WebSocket の送信バッファ(WebStream、変更なし)

- .NET の WebSocket は、送るたびにヘッダーとデータを並べるバッファを ArrayPool から借り、送り終えたら返す。ArrayPool はスレッドごとにバッファを持つので、送信のループが初めてのスレッドで動くと、借りられずに新しく作る
- ArrayPool のイベント(`System.Buffers.ArrayPoolEventSource`)で、クライアント1台を90秒調べた

| 配信 | 借りた回数 | 新しく作った回数 |
|:--|--:|--:|
| H.264(16 / 32 / 128 KB) | 2679 | 13(最初の20秒に10) |
| JPEG(64 KB) | 2680 | 3(最初に2) |

- 最初の後は、スレッドプールのスレッドが入れ替わったときと、送信が別のスレッドで終わったキーフレーム(128 KB)だけで、H.264 で約 2.5 KB/s
- 避けるには、送信をいつも同じスレッドで動かす(取込やエンコーダーのスレッドで送る)か、WebSocket のフレームを自分で書く必要がある。減る量に見合わないので、そのままにする

## 📨 送信の待ちの割当(WebStream)

- 送信の `FrameSender.SendAsync`(`async ValueTask`)は、送信が待ちに入るたびに、メソッドの状態を入れる箱を確保していた。720p の JPEG(約 150 KB)は Kestrel の出力が 64 KB で止まるので、ほぼ毎フレーム待つ
- `PoolingAsyncValueTaskMethodBuilder` で箱を使い回す

| 構成 | 変更前 | 変更後 |
|:--|--:|--:|
| 待ちに入る送信1回(単体の計測、2万回の平均) | 128 B | 0 B |

- 720p の JPEG をクライアント1台に送ると、30 fps で約 3.8 KB/s 減る。サーバー全体の割当(約 40〜60 KB/s、5秒ごとの値は ±10 KB/s ほどばらつく)では差がはっきりしない
- 既定の 480p(約 60 KB)は、ほとんど待たずに終わる
