# camera-tool

C#(WPF / ASP.NET Core)でカメラを使うアプリケーションを作成・検証するためのソリューションです。
カメラの制御には MediaFrameReader (Windows Runtime) を使い、低遅延・低アロケーションな実装を検証します。

## プロジェクト

| プロジェクト | 内容 |
|:--|:--|
| `src/CameraTool.Capture` | MediaFrameReader のラッパー(WPF に依存しない) |
| `src/CameraTool.Vision` | YUV の変換(AVX2 / SSSE3)、JPEG エンコード(WIC)、顔検出(ONNX Runtime + RFB-320) |
| `src/CameraTool.FaceViewer` | カメラ映像と顔検出の結果を表示する WPF アプリ |
| `src/CameraTool.WebStream` | カメラ映像をブラウザーへ配信する ASP.NET Core サーバー(WebSocket / MJPEG) |
| `tests/CameraTool.Vision.Tests` | Vision の単体テスト(xunit.v3) |

## 実行

```
dotnet run --project src/CameraTool.FaceViewer
```

設定は `appsettings.json` で指定し、コマンドライン引数でも上書きできます(例: `--Camera:Format=Nv12 --Camera:Width=1280 --Camera:Height=720`)。

| キー | 内容 | 既定値 |
|:--|:--|:--|
| `Camera:Name` | デバイス名。空なら先頭のデバイス | `ELECOM 2MP Webcam` |
| `Camera:Format` | `Yuy2` / `Nv12` | `Yuy2` |
| `Camera:Width` / `Height` / `Fps` | 解像度とフレームレート | `640` / `480` / `30` |
| `Camera:Conversion` | `Software`: ImageConverter で BGRA に変換 / `Reader`: MediaFrameReader が BGRA8 に変換 | `Software` |
| `Display:UpdateMode` | `Immediate`: フレーム到着時に Dispatcher で更新 / `Rendering`: CompositionTarget.Rendering で更新 | `Immediate` |
| `Detect:Enable` | 顔検出の有効/無効(画面からも切り替え可能) | `true` |
| `Detect:Model` | モデルファイル | `version-RFB-320.onnx` |
| `Detect:ConfidenceThreshold` / `IouThreshold` | 検出のしきい値と NMS の IoU | `0.7` / `0.3` |
| `Detect:IntraOpNumThreads` / `InterOpNumThreads` | ONNX Runtime のスレッド数 | `1` / `1` |

モデルは [Ultra-Light-Fast-Generic-Face-Detector-1MB](https://github.com/Linzaer/Ultra-Light-Fast-Generic-Face-Detector-1MB) の `version-RFB-320.onnx`(MIT ライセンス、`version-RFB-320-LICENSE.txt`)です。

`DOTNET_ENVIRONMENT=Development` で起動すると、5秒ごとの計測値がログ(`Debug` レベル)に出力されます。

## 計測結果

- 環境: ELECOM 2MP Webcam (VID_056E / PID_701E)、Windows 11 (26300)、.NET 10、Release ビルド
- 方法: 各構成を約30秒実行し、5秒ごとの値を平均(最大値は期間中の最大)

### 指標

| 指標 | 内容 |
|:--|:--|
| Capture latency | `MediaFrameReference.SystemRelativeTime` から FrameArrived まで。ほぼ1フレーム周期で、大半はカメラからの転送時間 |
| Process | FrameArrived の中でトリプルバッファへ書き込む時間(BGRA のコピー、または YUV からの変換) |
| Display latency | FrameArrived から WriteableBitmap へのコピーまで |
| CPU | プロセス全体の CPU 使用率(全コアに対する割合) |
| Allocated / GC | プロセス全体の割当量と GC 回数 |

### Phase 1 → Phase 2(YUY2 640x480)

| 項目 | Phase 1 | Phase 2 (Reader) | Phase 2 (Software) |
|:--|--:|--:|--:|
| フレームの読み取り | 投影 API(`SoftwareBitmap`) | COM vtable を直接呼ぶ | COM vtable を直接呼ぶ |
| BGRA への変換 | MediaFrameReader | MediaFrameReader | ImageConverter (AVX2) |
| GC | 約15回/秒(すべて gen2) | 0 | 0 |
| Allocated | 309 KB/s | 129 KB/s | 119 KB/s |
| Display latency(平均 / 最大) | 2.2 / 4.7 ms | 0.8 / 1.7 ms | 0.3 / 0.5 ms |

Phase 1 の値は Debug ビルドで計測したものです。GC は投影の `SoftwareBitmap` が GC のメモリプレッシャーを登録するために起きており、ビルド構成には関係ありません。

### 表示の更新方式(YUY2 640x480)

| 変換 | 更新方式 | 表示 fps | Display latency | Allocated |
|:--|:--|--:|--:|--:|
| Reader | Immediate | 29.8 | 0.8 / 1.7 ms | 129 KB/s |
| Reader | Rendering | 27.9 | 12.5 / 40.1 ms | 175 KB/s |
| Software | Immediate | 29.7 | 0.3 / 0.5 ms | 119 KB/s |
| Software | Rendering | 28.4 | 12.4 / 31.9 ms | 180 KB/s |

### 分かったこと

- **投影の `SoftwareBitmap` は gen2 GC を誘発する。** Dispose しても約4フレームに1回フル GC が起きる。フレームごとの経路を COM vtable の直接呼び出しにすると GC は 0 になる。
- **フォーマット**: YUY2 はカメラ本来の非圧縮形式で、Capture latency が最も小さい(640x480 まで)。NV12 は Windows 側で MJPG をデコードしたもので、解像度に応じて約 +1.5〜6 ms かかる。
- **色レンジ**: YUY2 はリミテッドレンジ(16-235)、MJPG 由来の NV12 はフルレンジ(0-255)で、どちらも BT.601。自前で変換するときは `MF_MT_VIDEO_NOMINAL_RANGE` に従う必要がある(フルレンジをリミテッドとして扱うと白飛び・黒つぶれが起きる)。
- **変換方式**: AVX2 の自前変換は 1080p でも 1 ms 以下で、CPU 使用率は MediaFrameReader の BGRA8 変換の 1/2〜1/3。遅延はほぼ同じなので、既定値を `Software` にした。
- **表示の更新方式**: `Rendering` は描画ティックまで待つため平均約12 ms 遅れ、フレームの取りこぼしも起きる。`Immediate` を既定値にした。
- **残りの割当(約120〜130 KB/s)**: 約6割は計測値パネルの文字描画(1秒ごと)、約3割はフレームごとの Dispatcher 呼び出しで、ほかに `WriteableBitmap.Lock` と WinRT のイベント引数が少しずつある。映像の経路だけなら1フレームあたり約1.7 KB で、計測中に GC は起きていない。

## 顔検出

### 処理の流れ

```
FrameArrived (取込スレッド)
  ├─ BGRA に変換してトリプルバッファへ → 表示
  └─ 検出器が空いていれば: 320x240 に縮小 + RGB 化 + (x-127)/128 でテンソルへ(前処理)
                            ↓
                     検出スレッド: ONNX Runtime で推論 → しきい値 → NMS → 顔枠を表示
```

- 検出は専用スレッドで動き、処理中に届いたフレームは検出せずに飛ばします。推論が取込や表示を待たせることはありません。
- ONNX Runtime は IoBinding で入出力を事前確保したバッファに結び付けているので、推論1回あたりの割当は約21バイトです。
- 顔枠のラベルは子 Visual にして、文字が変わったときだけ描き直し、位置は `Offset` で動かしています。

### 計測結果(Release ビルド、変換は Software、表示は Immediate)

| 構成 | 検出 fps | 前処理 | 推論 | Capture latency | Display latency | CPU | Allocated |
|:--|--:|--:|--:|--:|--:|--:|--:|
| YUY2 640x480 検出なし | - | - | - | 33.9 / 48.6 ms | 0.8 / 18.6 ms | 0.30 % | 118 KB/s |
| YUY2 640x480 1スレッド | 29.5 | 0.93 / 1.25 ms | 7.92 / 14.01 ms | 34.0 / 48.5 ms | 0.4 / 1.2 ms | 1.30 % | 208 KB/s |
| YUY2 640x480 2スレッド | 29.5 | 0.99 / 1.18 ms | 6.84 / 9.56 ms | 34.0 / 48.5 ms | 0.6 / 5.2 ms | 5.29 % | 190 KB/s |
| YUY2 640x480 4スレッド | 30.0 | 0.95 / 1.17 ms | 4.49 / 5.96 ms | 34.0 / 48.6 ms | 0.9 / 29.9 ms | 13.48 % | 239 KB/s |
| NV12 1280x720 検出なし | - | - | - | 37.2 / 52.3 ms | 1.0 / 7.6 ms | 0.26 % | 113 KB/s |
| NV12 1280x720 1スレッド | 29.8 | 0.91 / 1.47 ms | 8.36 / 11.53 ms | 37.2 / 52.0 ms | 1.0 / 8.1 ms | 1.58 % | 201 KB/s |

スレッド数は `Detect:IntraOpNumThreads` です。どの構成でも取込・表示は約30fpsで、GC は0回でした。

### 分かったこと

- **1スレッドでもカメラと同じ約30fpsで検出できる**(推論 約8 ms)。検出を有効にしても Capture latency と Display latency は変わらない。
- **推論スレッドを増やすと CPU 使用率が大きく増える。** 4スレッドで推論は約4.5 ms まで縮むが、ONNX Runtime のスレッドがスピン待ちするため CPU は約10倍になり、表示にも時々遅れが出た。既定値は1スレッドにした。
- **前処理は約0.9 ms**(スカラー実装、入力サイズは 320x240 固定なので解像度にほぼ依存しない)。
- **割当は検出で約 +80〜90 KB/s**(顔枠の更新と Dispatcher 呼び出し)。ラベルを毎回 `FormattedText` で描くと約 +150〜230 KB/s、文字を図形にして `DrawImage` で描くと約 1.7 MB/s まで増えたため、子 Visual を使う方式にした。
- **モデルの警告**: このモデルは古い形式で、重みがグラフ入力にも含まれるため、ONNX Runtime の定数畳み込みなどの最適化が効かない(警告はログレベルで抑えている)。重みをグラフ入力から外したモデルにすれば、推論がさらに速くなる可能性がある。

## Web 配信

`src/CameraTool.WebStream` は、カメラ映像を ASP.NET Core からブラウザーへ配信するサーバーです。

```
dotnet run --project src/CameraTool.WebStream
```

`http://localhost:5080` で待ち受けます(ローカルのみ、認証なし)。ブラウザーで開くとビューアーが表示されます。FaceViewer とはカメラを同時に使えません(どちらも排他モードで開くため)。

| パス | 内容 |
|:--|:--|
| `/` | ビューアー(WebSocket / MJPEG の切り替え、顔検出の ON/OFF、クライアントとサーバーの計測値) |
| `/ws` | WebSocket 配信(バイナリ: ヘッダー + JPEG。顔検出の結果もヘッダーに入る) |
| `/stream.mjpg` | MJPEG(`multipart/x-mixed-replace`)。`<img>` や VLC でそのまま見られる(顔枠は付かない) |
| `/snapshot.jpg` | 次のフレームを1枚返す |
| `/api/status` | サーバーの計測値(JSON、1秒ごとに更新) |
| `PUT /api/detection` | 顔検出の ON/OFF(`{"enabled": true}`) |

| キー | 内容 | 既定値 |
|:--|:--|:--|
| `Urls` | 待ち受けるアドレス | `http://localhost:5080` |
| `Camera:Name` / `Format` / `Width` / `Height` / `Fps` | FaceViewer と同じ | `ELECOM 2MP Webcam` / `Yuy2` / `640` / `480` / `30` |
| `Stream:Quality` | JPEG の品質(1〜100) | `80` |
| `Detect:*` | 顔検出(FaceViewer と同じ) | `Enable` は `true` |

### 処理の流れ

```
FrameArrived (取込スレッド)
  ├─ クライアントがいれば、フルレンジの NV12 を WIC で JPEG 化(平面 YCbCr のまま渡す)
  │    ・MJPG 由来の NV12: カメラのバッファをそのまま渡す
  │    ・YUY2: フルレンジの NV12 に変換してから渡す
  │  → プールしたバッファに、ヘッダー(最新の顔検出の結果を含む)と JPEG を書き、FrameHub に公開(最新の1枚だけを持つ)
  │             ↓
  │  接続ごとの送信ループ: 新しいフレームを待って送信(送信中に届いたフレームは飛ばす)
  │
  └─ エンコードの後、検出器が空いていれば 320x240 のテンソルを作る
                ↓
     検出スレッド: ONNX Runtime で推論 → 結果は次のフレームのヘッダーに入る
```

- 1フレームを1回だけエンコードし、全クライアントに同じバッファを送ります。バッファは参照カウントで管理し、全員が送り終えたらプールに戻します。
- 待ち合わせは使い回す `IValueTaskSource` で行い、フレームごとに Task を作りません。
- クライアントがいないときは、変換もエンコードも顔検出もしません。
- 顔検出は配信より後に処理するので、配信の遅延には影響しません。そのかわり、顔枠は1フレーム前の検出結果です。

### WebSocket のメッセージ

バイナリの1メッセージが1フレームです(リトルエンディアン)。

| オフセット | 型 | 内容 |
|--:|:--|:--|
| 0 | uint16 | バージョン(1) |
| 2 | uint16 | ヘッダー長(JPEG の開始位置) |
| 4 | uint16 | 幅 |
| 6 | uint16 | 高さ |
| 8 | uint32 | 連番 |
| 12 | uint32 | フラグ(bit 0: 顔検出の結果あり) |
| 16 | float64 | 取込時刻(Unix ms) |
| 24 | float64 | エンコード完了時刻(Unix ms) |
| 32 | uint32 | 顔を検出したフレームの連番(0: まだ検出していない) |
| 36 | uint16 | 顔の数 |
| 38 | uint16 | 予約 |
| 40 + 20n | float32 × 5 | 顔枠(左・上・右・下を 0〜1 で正規化)と信頼度 |

オフセット 32 以降は、顔検出が有効なとき(フラグの bit 0)だけ付きます。JPEG はヘッダー長の位置から始まるので、顔の数でヘッダーの長さが変わっても読み飛ばせます。

取込時刻は、カメラのタイムスタンプ(QPC)をエンコード完了時にサーバーの時計で Unix 時刻に換算したものです。ブラウザーが同じ PC で動いていれば、取込から受信・描画までの遅延を測れます。

### 指標

| 指標 | 内容 |
|:--|:--|
| 到着→配信可能 | FrameArrived から FrameHub に公開するまで(変換・エンコードを含む) |
| 配信可能→送信開始 / 送信完了 | 公開から、各クライアントへの送信を始めるまで / OS に渡し終えるまで |
| 配信可能→受信 | 公開から、クライアントがメッセージ全体を受け取るまで |
| 受信 / 描画 | カメラのタイムスタンプから、クライアントが受け取るまで / canvas に描くまで |

### 計測結果(Phase W1)

- 構成: WinRT の `BitmapEncoder`(WIC)で BGRA から JPEG(品質80)に変換し、バッファはフレームごとに確保。GC は ASP.NET Core 既定の Server GC
- 方法: Release ビルド、クライアント1台で約30秒。受信側はヘッドレスの WebSocket クライアント(.NET)と組み込みブラウザー(Chromium)で、GC とメモリは dotnet-counters で計測

### 分かったこと

- **サーバー内の遅延はほぼエンコードの時間**: 到着から配信可能まで 1.9 / 3.9 / 7.6 ms(480p / 720p / 1080p)で、その大半が WIC のエンコード。AVX2 の変換は 0.13〜0.75 ms。
- **ローカルでの送信は速い**: 配信可能から受信まで、480p・720p では 0.2〜0.4 ms。1080p(約270 KB/フレーム)は中央値 0.6 ms だが、ときどき 20 ms 前後の遅れが出る。
- **取込から描画までの遅延の大半はカメラ側**: カメラ側(約34〜40 ms)+ サーバー(2〜8 ms)+ ブラウザーのデコード(1.7〜6.6 ms)。
- **WinRT の `BitmapEncoder` は、ネイティブのメモリを GC まで手放さない**: GC ヒープは約30 MB なのに、ワーキングセットが1フレームあたり約1.4 MB ずつ増え、GC(ファイナライザー)のときにだけ減る。Server GC は GC の間隔が長いため、480p でも最大約1.3 GB まで増えた(Workstation GC では約370 MB)。
- **720p 以上では、JPEG のバッファ(85 KB 超)が LOH に入り、gen2 GC が3〜4秒に1回起きる**。停止時間は合計 10 ms 程度と小さいが、割当は 4.9〜8.6 MB/s ある。
- エンコーダーとバッファの扱いは、Phase W2 で改善した(下記)。

### 計測結果(Phase W2)

変更点

- **エンコーダー**: WIC を COM の vtable で直接呼ぶ `JpegEncoder`(Vision)に置き換えた。NV12 を平面 YCbCr(8bppY + 16bppCbCr)のまま渡すので色変換がなく、結果はプールしたバッファへ直接書き込む。WIC のオブジェクトはフレームごとにその場で解放する
- **入力**: MJPG 由来の NV12(フルレンジ)はカメラのバッファをコピーせずに渡す。YUY2 は `ImageConverter.Yuy2ToNv12`(SSSE3)でフルレンジの NV12 に変換する。リミテッドレンジの NV12 は `Nv12ToFullRange` で広げる
- **スレッド**: トリプルバッファとエンコードのループをやめ、取込スレッドでそのままエンコードして公開する
- **バッファと待ち合わせ**: 上の「処理の流れ」のとおり、参照カウントとプール、使い回す `IValueTaskSource` にした

JPEG エンコーダーの比較(カメラの1フレーム、品質80、1回あたり)

| 解像度 | WinRT BitmapEncoder(BGRA) | WIC 直接(BGR24) | WIC 直接(平面 NV12) |
|:--|--:|--:|--:|
| 640x480 | 1.38 ms / 79 KB 割当 / 35.03 dB | 1.00 ms(+BGR24 への変換 0.35 ms) | **0.86 ms** / 35.07 dB |
| 1280x720 | 3.95 ms / 177 KB / 36.22 dB | 2.71 ms(+1.09 ms) | **2.24 ms** / 36.29 dB |
| 1920x1080 | 8.53 ms / 327 KB / 37.33 dB | 5.43 ms(+2.48 ms) | **4.31 ms** / 37.36 dB |

dB は元の画像との PSNR です。WIC の JPEG エンコーダーは BGRA を受け付けず、24bppBGR への変換が要ります。平面 NV12 がいちばん速く、色変換が1回減るので画質もわずかに良いため、こちらだけを使います(設定での切り替えは設けていません)。

### 分かったこと(Phase W2)

- **WIC は COM で直接呼び、平面 NV12 で渡すのが最速**: WinRT 経由より 1.6〜2倍速く、GC の割当もない。MJPG 由来の NV12 はカメラのバッファをそのまま渡せるので、変換もいらない。
- **サーバー内の遅延は約半分になった**: 到着から配信可能まで 0.9 / 2.1 / 4.3 ms(480p / 720p / 1080p)。ほぼエンコードの時間で、取込スレッドでそのままエンコードするため、キューやスレッドの切り替えによる待ちはない。
- **メモリは一定**: WIC のオブジェクトをその場で解放し、バッファをプールしたので、ワーキングセットは約110 MB のまま、定常状態では gen2 GC が起きない。配信経路のコードはフレームごとの割当がなく(割当トレースで確認)、残りの 40〜100 KB/s は WinRT のイベント引数(約0.5 KB/フレーム)と、ManagedWebSocket・Kestrel の内部。
- **1080p の遅れの原因は、受信側の TCP**: サーバーは配信可能から約0.7 ms で送り終えているのに、受信側のソケットのバッファが既定のままだと、約290 KB のメッセージで 10〜25 ms の遅れが約2割のフレームに出る。.NET のクライアントで受信バッファを 4 MB にすると消えた(0.66 ms)。ブラウザー(Chromium)でも 1080p では平均 6〜11 ms(最大 約40 ms)の遅れがあり(480p でもときどき出た)、ブラウザーの設定はサーバーからは変えられない。遅延を最小にしたい場合は、解像度や品質を下げてフレームを小さくする。
- **ブラウザーまでの遅延の大半は、引き続きカメラ側**(約34〜40 ms)。720p ではサーバーの改善分(約2 ms)がそのまま描画までの遅延に表れた。
- **複数クライアント**: エンコードは1回のままで、720p では1台増えるごとの CPU の増加は約0.1 %(全コア比)。

### 計測結果(Phase W3: 顔検出)

構成は W2 と同じで、`Detect:Enable` を切り替えて比べました(クライアント1台、約30秒、平均)。

|:--|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| YUY2 640x480 検出なし | − | − | − | 0.87 ms | 35.1 ms | 0.25 ms | 0.21 % | 45 KB/s | 144 MB |

ブラウザーでは、顔枠と信頼度が映像に重なって表示され、検出の遅れ(フレームの連番 − 検出したフレームの連番)は1フレームでした。

### 分かったこと(Phase W3)

- **顔検出は配信の遅延に影響しない**: 到着→配信可能、受信までの遅延とも、検出の有無で差は誤差の範囲。前処理はエンコードの後に取込スレッドで行い(約0.8 ms)、推論は専用のスレッドで行うため。
- **増えるのは CPU だけ**: 推論 約7.2 ms × 30fps で、1コアの約24 %(全コア比で約1 %)。割当はほぼ増えない(推論1回あたり約21バイト)。
- **顔枠は1フレーム遅れる**: フレームを公開する時点では、まだそのフレームの推論が終わっていないため、直前のフレームの結果を付けている。検出を待ってから公開すると、配信が推論の時間(約8 ms)だけ遅れるので、遅延の小さいほうを選んだ。
- **ワーキングセットは約35 MB 増える**: ONNX Runtime とモデルを起動時に読み込むため(画面から ON/OFF できるように、検出が OFF でも読み込んでいる)。
