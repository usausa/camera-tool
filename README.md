# camera-tool

C#(WPF / ASP.NET Core)でカメラを使うアプリケーションを作成・検証するためのソリューションです。
カメラの制御には MediaFrameReader (Windows Runtime) を使い、低遅延・低アロケーションな実装を検証します。

## プロジェクト

| プロジェクト | 内容 |
|:--|:--|
| `src/CameraTool.Capture` | MediaFrameReader のラッパー(WPF に依存しない) |
| `src/CameraTool.Vision` | YUV の変換(AVX2 / SSSE3)、JPEG エンコード(WIC)、顔検出(ONNX Runtime + RFB-320)、動体検知、検知範囲 |
| `src/CameraTool.FaceViewer` | カメラ映像と顔検出・動体検知の結果を表示し、検知範囲を編集する WPF アプリ |
| `src/CameraTool.WebStream` | カメラ映像をブラウザーへ配信する ASP.NET Core サーバー(WebSocket / MJPEG) |
| `tests/CameraTool.Vision.Tests` | Vision の単体テスト(xunit.v3) |

## 実行

```
dotnet run --project src/CameraTool.FaceViewer
```

設定は `appsettings.json` で指定し、コマンドライン引数でも上書きできます(例: `--Camera:Format=Nv12 --Camera:Width=1280 --Camera:Height=720`)。

| キー | 内容 | 既定値 |
|:--|:--|:--|
| `Camera:Name` | デバイス名。空なら先頭のデバイス | `ELECOM 2MP Webcam` |
| `Camera:Format` | `Yuy2` / `Nv12` | `Yuy2` |
| `Camera:Width` / `Height` / `Fps` | 解像度とフレームレート | `640` / `480` / `30` |
| `Camera:Conversion` | `Software`: ImageConverter で BGRA に変換 / `Reader`: MediaFrameReader が BGRA8 に変換 | `Software` |
| `Display:UpdateMode` | `Immediate`: フレーム到着時に Dispatcher で更新 / `Rendering`: CompositionTarget.Rendering で更新 | `Immediate` |
| `Detect:Enable` | 顔検出の有効/無効(画面からも切り替え可能) | `true` |
| `Detect:Model` | モデルファイル | `version-RFB-320.onnx` |
| `Detect:ConfidenceThreshold` / `IouThreshold` | 検出のしきい値と NMS の IoU | `0.7` / `0.3` |
| `Detect:IntraOpNumThreads` / `InterOpNumThreads` | ONNX Runtime のスレッド数 | `1` / `1` |
| `Detect:MotionGate` | 動きがない間は、顔検出を `IdleInterval` ごとにだけ行う(画面からも切り替え可能) | `false` |
| `Detect:IdleInterval` / `MotionHoldTime` | 動きがない間の検出の間隔 / 最後の動きから「動きあり」とみなす時間(ms) | `1000` / `2000` |
| `Motion:Enable` | 動体検知の有効/無効(画面からも切り替え可能) | `true` |
| `Motion:Threshold` | 背景との輝度差のしきい値(0〜255、小さいほど敏感) | `25` |
| `Motion:CellRatio` | マスの中で変化した画素の割合がこれ以上なら、動いたマスとする | `0.2` |
| `Motion:MinArea` | 動いたマスの割合(検知範囲のマス数に対する)がこれ以上なら「動きあり」とする | `0.005` |
| `Motion:BackgroundRate` | 背景の更新率(1フレームあたり) | `0.05` |
| `Area:Path` | 検知範囲のファイル(環境変数を展開、相対パスは exe のフォルダーから) | `%LOCALAPPDATA%\CameraTool\FaceViewer\area.json` |

モデルは [Ultra-Light-Fast-Generic-Face-Detector-1MB](https://github.com/Linzaer/Ultra-Light-Fast-Generic-Face-Detector-1MB) の `version-RFB-320.onnx`(MIT ライセンス、`version-RFB-320-LICENSE.txt`)です。

`DOTNET_ENVIRONMENT=Development` で起動すると、5秒ごとの計測値がログ(`Debug` レベル)に出力されます。

## 計測結果

- 環境: ELECOM 2MP Webcam (VID_056E / PID_701E)、Windows 11 (26300)、.NET 10、Release ビルド
- 方法: 各構成を約30秒実行し、5秒ごとの値を平均(最大値は期間中の最大)

### 指標

| 指標 | 内容 |
|:--|:--|
| Capture latency | `MediaFrameReference.SystemRelativeTime` から FrameArrived まで。ほぼ1フレーム周期で、大半はカメラからの転送時間 |
| Process | FrameArrived の中でトリプルバッファへ書き込む時間(BGRA のコピー、または YUV からの変換) |
| Display latency | FrameArrived から WriteableBitmap へのコピーまで |
| CPU | プロセス全体の CPU 使用率(全コアに対する割合) |
| Allocated / GC | プロセス全体の割当量と GC 回数 |

### Phase 1 → Phase 2(YUY2 640x480)

| 項目 | Phase 1 | Phase 2 (Reader) | Phase 2 (Software) |
|:--|--:|--:|--:|
| フレームの読み取り | 投影 API(`SoftwareBitmap`) | COM vtable を直接呼ぶ | COM vtable を直接呼ぶ |
| BGRA への変換 | MediaFrameReader | MediaFrameReader | ImageConverter (AVX2) |
| GC | 約15回/秒(すべて gen2) | 0 | 0 |
| Allocated | 309 KB/s | 129 KB/s | 119 KB/s |
| Display latency(平均 / 最大) | 2.2 / 4.7 ms | 0.8 / 1.7 ms | 0.3 / 0.5 ms |

Phase 1 の値は Debug ビルドで計測したものです。GC は投影の `SoftwareBitmap` が GC のメモリプレッシャーを登録するために起きており、ビルド構成には関係ありません。

### 表示の更新方式(YUY2 640x480)

| 変換 | 更新方式 | 表示 fps | Display latency | Allocated |
|:--|:--|--:|--:|--:|
| Reader | Immediate | 29.8 | 0.8 / 1.7 ms | 129 KB/s |
| Reader | Rendering | 27.9 | 12.5 / 40.1 ms | 175 KB/s |

### 分かったこと

- **投影の `SoftwareBitmap` は gen2 GC を誘発する。** Dispose しても約4フレームに1回フル GC が起きる。フレームごとの経路を COM vtable の直接呼び出しにすると GC は 0 になる。
- **フォーマット**: YUY2 はカメラ本来の非圧縮形式で、Capture latency が最も小さい(640x480 まで)。NV12 は Windows 側で MJPG をデコードしたもので、解像度に応じて約 +1.5〜6 ms かかる。
- **色レンジ**: YUY2 はリミテッドレンジ(16-235)、MJPG 由来の NV12 はフルレンジ(0-255)で、どちらも BT.601。自前で変換するときは `MF_MT_VIDEO_NOMINAL_RANGE` に従う必要がある(フルレンジをリミテッドとして扱うと白飛び・黒つぶれが起きる)。
- **変換方式**: AVX2 の自前変換は 1080p でも 1 ms 以下で、CPU 使用率は MediaFrameReader の BGRA8 変換の 1/2〜1/3。遅延はほぼ同じなので、既定値を `Software` にした。
- **表示の更新方式**: `Rendering` は描画ティックまで待つため平均約12 ms 遅れ、フレームの取りこぼしも起きる。`Immediate` を既定値にした。
- **残りの割当(約120〜130 KB/s)**: 約6割は計測値パネルの文字描画(1秒ごと)、約3割はフレームごとの Dispatcher 呼び出しで、ほかに `WriteableBitmap.Lock` と WinRT のイベント引数が少しずつある。映像の経路だけなら1フレームあたり約1.7 KB で、計測中に GC は起きていない。WinRT のイベント引数は、後で COM の直接購読に変えてなくした(「追加の改善」を参照)。

## 顔検出

### 処理の流れ

```
FrameArrived (取込スレッド)
  ├─ BGRA に変換してトリプルバッファへ → 表示
  └─ 検出器が空いていれば: 320x240 に縮小 + RGB 化 + (x-127)/128 でテンソルへ(前処理)
                            ↓
                     検出スレッド: ONNX Runtime で推論 → しきい値 → NMS → 顔枠を表示
```

- 検出は専用スレッドで動き、処理中に届いたフレームは検出せずに飛ばします。推論が取込や表示を待たせることはありません。
- ONNX Runtime は IoBinding で入出力を事前確保したバッファに結び付けているので、推論1回あたりの割当は約21バイトです。
- 顔枠のラベルは子 Visual にして、文字が変わったときだけ描き直し、位置は `Offset` で動かしています。

### 計測結果(Release ビルド、変換は Software、表示は Immediate)

| 構成 | 検出 fps | 前処理 | 推論 | Capture latency | Display latency | CPU | Allocated |
|:--|--:|--:|--:|--:|--:|--:|--:|
| YUY2 640x480 検出なし | - | - | - | 33.9 / 48.6 ms | 0.8 / 18.6 ms | 0.30 % | 118 KB/s |
| YUY2 640x480 1スレッド | 29.5 | 0.93 / 1.25 ms | 7.92 / 14.01 ms | 34.0 / 48.5 ms | 0.4 / 1.2 ms | 1.30 % | 208 KB/s |
| YUY2 640x480 2スレッド | 29.5 | 0.99 / 1.18 ms | 6.84 / 9.56 ms | 34.0 / 48.5 ms | 0.6 / 5.2 ms | 5.29 % | 190 KB/s |
| YUY2 640x480 4スレッド | 30.0 | 0.95 / 1.17 ms | 4.49 / 5.96 ms | 34.0 / 48.6 ms | 0.9 / 29.9 ms | 13.48 % | 239 KB/s |
| NV12 1280x720 検出なし | - | - | - | 37.2 / 52.3 ms | 1.0 / 7.6 ms | 0.26 % | 113 KB/s |
| NV12 1280x720 1スレッド | 29.8 | 0.91 / 1.47 ms | 8.36 / 11.53 ms | 37.2 / 52.0 ms | 1.0 / 8.1 ms | 1.58 % | 201 KB/s |

スレッド数は `Detect:IntraOpNumThreads` です。どの構成でも取込・表示は約30fpsで、GC は0回でした。

### 分かったこと

- **1スレッドでもカメラと同じ約30fpsで検出できる**(推論 約8 ms)。検出を有効にしても Capture latency と Display latency は変わらない。
- **推論スレッドを増やすと CPU 使用率が大きく増える。** 4スレッドで推論は約4.5 ms まで縮むが、ONNX Runtime のスレッドがスピン待ちするため CPU は約10倍になり、表示にも時々遅れが出た。既定値は1スレッドにした。
- **前処理は約0.9 ms**(スカラー実装、入力サイズは 320x240 固定なので解像度にほぼ依存しない)。後で AVX2 にして約0.3 ms になった(「追加の改善」を参照)。
- **割当は検出で約 +80〜90 KB/s**(顔枠の更新と Dispatcher 呼び出し)。ラベルを毎回 `FormattedText` で描くと約 +150〜230 KB/s、文字を図形にして `DrawImage` で描くと約 1.7 MB/s まで増えたため、子 Visual を使う方式にした。
- **モデルの警告**: このモデルは古い形式で、重みがグラフ入力にも含まれるため、ONNX Runtime の定数畳み込みなどの最適化が効かない(警告はログレベルで抑えている)。重みをグラフ入力から外したモデルにすれば、推論がさらに速くなる可能性がある。

## Web 配信

`src/CameraTool.WebStream` は、カメラ映像を ASP.NET Core からブラウザーへ配信するサーバーです。

```
dotnet run --project src/CameraTool.WebStream
```

`http://localhost:5080` で待ち受けます(ローカルのみ、認証なし)。ブラウザーで開くとビューアーが表示されます。FaceViewer とはカメラを同時に使えません(どちらも排他モードで開くため)。

| パス | 内容 |
|:--|:--|
| `/` | ビューアー(WebSocket / MJPEG の切り替え、顔検出・動体検知の ON/OFF、検知範囲の編集、クライアントとサーバーの計測値) |
| `/ws` | WebSocket 配信(バイナリ: ヘッダー + JPEG。顔検出と動体検知の結果もヘッダーに入る) |
| `/stream.mjpg` | MJPEG(`multipart/x-mixed-replace`)。`<img>` や VLC でそのまま見られる(顔枠や動いたマスは付かない) |
| `/snapshot.jpg` | 次のフレームを1枚返す |
| `/api/status` | サーバーの計測値(JSON、1秒ごとに更新) |
| `PUT /api/detection` | 顔検出の ON/OFF と、動きとの連動(`{"enabled": true, "motionGate": true}`。指定した項目だけ変わる) |
| `PUT /api/motion` | 動体検知の ON/OFF(`{"enabled": true}`) |
| `GET /api/area` | 検知範囲(`{"columns": 32, "rows": 24, "cells": [...]}`。ファイルと同じ形式) |
| `PUT /api/area` | 検知範囲を変える(GET と同じ形式。すぐ反映してファイルに保存する。形式が違えば 400) |

| キー | 内容 | 既定値 |
|:--|:--|:--|
| `Urls` | 待ち受けるアドレス | `http://localhost:5080` |
| `Camera:Name` / `Format` / `Width` / `Height` / `Fps` | FaceViewer と同じ | `ELECOM 2MP Webcam` / `Yuy2` / `640` / `480` / `30` |
| `Stream:Quality` | JPEG の品質(1〜100) | `80` |
| `Detect:*` | 顔検出と動きとの連動(FaceViewer と同じ) | `Enable` は `true`、`MotionGate` は `false` |
| `Motion:*` | 動体検知(FaceViewer と同じ) | `Enable` は `true` |
| `Area:Path` | 検知範囲のファイル(FaceViewer と同じ形式) | `%LOCALAPPDATA%\CameraTool\WebStream\area.json` |

### 処理の流れ

```
FrameArrived (取込スレッド)
  ├─ クライアントがいれば、フルレンジの NV12 を WIC で JPEG 化(平面 YCbCr のまま渡す)
  │    ・MJPG 由来の NV12: カメラのバッファをそのまま渡す
  │    ・YUY2: フルレンジの NV12 に変換してから渡す
  │  → プールしたバッファに、ヘッダー(最新の顔検出の結果を含む)と JPEG を書き、FrameHub に公開(最新の1枚だけを持つ)
  │             ↓
  │  接続ごとの送信ループ: 新しいフレームを待って送信(送信中に届いたフレームは飛ばす)
  │
  ├─ エンコードの後、検知範囲の中で動体検知 → 結果は次のフレームのヘッダーに入る
  │
  └─ 検出器が空いていれば 320x240 のテンソルを作る(連動時は、動きがない間は間隔を空ける)
                ↓
     検出スレッド: ONNX Runtime で推論 → 範囲外の顔を除き、結果は次のフレームのヘッダーに入る
```

- 1フレームを1回だけエンコードし、全クライアントに同じバッファを送ります。バッファは参照カウントで管理し、全員が送り終えたらプールに戻します。
- 待ち合わせは使い回す `IValueTaskSource` で行い、フレームごとに Task を作りません。
- クライアントがいないときは、変換もエンコードも動体検知も顔検出もしません。
- 顔検出は配信より後に処理するので、配信の遅延には影響しません。そのかわり、顔枠は1フレーム前の検出結果です。

### WebSocket のメッセージ

バイナリの1メッセージが1フレームです(リトルエンディアン)。

| オフセット | 型 | 内容 |
|--:|:--|:--|
| 0 | uint16 | バージョン(1) |
| 2 | uint16 | ヘッダー長(JPEG の開始位置) |
| 4 | uint16 | 幅 |
| 6 | uint16 | 高さ |
| 8 | uint32 | 連番 |
| 12 | uint32 | フラグ(bit 0: 顔検出の結果あり、bit 1: 動体検知の結果あり) |
| 16 | float64 | 取込時刻(Unix ms) |
| 24 | float64 | エンコード完了時刻(Unix ms) |
| 32 | uint32 | 顔を検出したフレームの連番(0: まだ検出していない) |
| 36 | uint16 | 顔の数 |
| 38 | uint16 | 予約 |
| 40 + 20n | float32 × 5 | 顔枠(左・上・右・下を 0〜1 で正規化)と信頼度 |

オフセット 32 以降の顔のセクションは、顔検出が有効なとき(フラグの bit 0)だけ付きます。動体検知が有効なとき(フラグの bit 1)は、その後ろ(顔のセクションがなければオフセット 32)に動きのセクションが付きます。

| 相対オフセット | 型 | 内容 |
|--:|:--|:--|
| 0 | uint32 | 動きを判定したフレームの連番(0: まだ判定していない) |
| 4 | uint16 | 動いたマスの数 |
| 6 | uint8 | 列数(32) |
| 7 | uint8 | 行数(24) |
| 8 | byte × 96 | マスク(行優先、各バイトの下位ビットから) |

JPEG はヘッダー長の位置から始まるので、顔の数や付いているセクションでヘッダーの長さが変わっても読み飛ばせます。

取込時刻は、カメラのタイムスタンプ(QPC)をエンコード完了時にサーバーの時計で Unix 時刻に換算したものです。ブラウザーが同じ PC で動いていれば、取込から受信・描画までの遅延を測れます。

### 指標

| 指標 | 内容 |
|:--|:--|
| 到着→配信可能 | FrameArrived から FrameHub に公開するまで(変換・エンコードを含む) |
| 配信可能→送信開始 / 送信完了 | 公開から、各クライアントへの送信を始めるまで / OS に渡し終えるまで |
| 配信可能→受信 | 公開から、クライアントがメッセージ全体を受け取るまで |
| 受信 / 描画 | カメラのタイムスタンプから、クライアントが受け取るまで / canvas に描くまで |

| 構成 | GC(gen0 / gen1 / gen2) | GC の停止時間 | ワーキングセットの最大 |
|:--|--:|--:|--:|
| YUY2 640x480 | 1 / 0 / 1 | 5.3 ms | 約1.3 GB(90秒間) |
| NV12 1280x720 | 1 / 0 / 8 | 9.4 ms | 649 MB |
| NV12 1920x1080 | 2 / 0 / 9 | 12.1 ms | 1.3 GB |
| YUY2 640x480(Workstation GC) | 1 / 1 / 2 | 15.8 ms | 370 MB |

どの構成も約30fpsで、取りこぼしはありませんでした。MJPEG でも同じように配信できます(curl で3秒間に89フレーム)。

### 分かったこと

- **サーバー内の遅延はほぼエンコードの時間**: 到着から配信可能まで 1.9 / 3.9 / 7.6 ms(480p / 720p / 1080p)で、その大半が WIC のエンコード。AVX2 の変換は 0.13〜0.75 ms。
- **ローカルでの送信は速い**: 配信可能から受信まで、480p・720p では 0.2〜0.4 ms。1080p(約270 KB/フレーム)は中央値 0.6 ms だが、ときどき 20 ms 前後の遅れが出る。
- **取込から描画までの遅延の大半はカメラ側**: カメラ側(約34〜40 ms)+ サーバー(2〜8 ms)+ ブラウザーのデコード(1.7〜6.6 ms)。
- **WinRT の `BitmapEncoder` は、ネイティブのメモリを GC まで手放さない**: GC ヒープは約30 MB なのに、ワーキングセットが1フレームあたり約1.4 MB ずつ増え、GC(ファイナライザー)のときにだけ減る。Server GC は GC の間隔が長いため、480p でも最大約1.3 GB まで増えた(Workstation GC では約370 MB)。
- **720p 以上では、JPEG のバッファ(85 KB 超)が LOH に入り、gen2 GC が3〜4秒に1回起きる**。停止時間は合計 10 ms 程度と小さいが、割当は 4.9〜8.6 MB/s ある。
- エンコーダーとバッファの扱いは、Phase W2 で改善した(下記)。

### 計測結果(Phase W2)

変更点

- **エンコーダー**: WIC を COM の vtable で直接呼ぶ `JpegEncoder`(Vision)に置き換えた。NV12 を平面 YCbCr(8bppY + 16bppCbCr)のまま渡すので色変換がなく、結果はプールしたバッファへ直接書き込む。WIC のオブジェクトはフレームごとにその場で解放する
- **入力**: MJPG 由来の NV12(フルレンジ)はカメラのバッファをコピーせずに渡す。YUY2 は `ImageConverter.Yuy2ToNv12`(SSSE3)でフルレンジの NV12 に変換する。リミテッドレンジの NV12 は `Nv12ToFullRange` で広げる
- **スレッド**: トリプルバッファとエンコードのループをやめ、取込スレッドでそのままエンコードして公開する
- **バッファと待ち合わせ**: 上の「処理の流れ」のとおり、参照カウントとプール、使い回す `IValueTaskSource` にした

| 1920x1080 | 8.53 ms / 327 KB / 37.33 dB | 5.43 ms(+2.48 ms) | **4.31 ms** / 37.36 dB |

### 分かったこと(Phase W2)

- **WIC は COM で直接呼び、平面 NV12 で渡すのが最速**: WinRT 経由より 1.6〜2倍速く、GC の割当もない。MJPG 由来の NV12 はカメラのバッファをそのまま渡せるので、変換もいらない。
- **サーバー内の遅延は約半分になった**: 到着から配信可能まで 0.9 / 2.1 / 4.3 ms(480p / 720p / 1080p)。ほぼエンコードの時間で、取込スレッドでそのままエンコードするため、キューやスレッドの切り替えによる待ちはない。
- **メモリは一定**: WIC のオブジェクトをその場で解放し、バッファをプールしたので、ワーキングセットは約110 MB のまま、定常状態では gen2 GC が起きない。配信経路のコードはフレームごとの割当がなく(割当トレースで確認)、残りの 40〜100 KB/s は WinRT のイベント引数(約0.5 KB/フレーム。後でなくした)と、ManagedWebSocket・Kestrel の内部。
- **1080p の遅れの原因は、受信側の TCP**: サーバーは配信可能から約0.7 ms で送り終えているのに、受信側のソケットのバッファが既定のままだと、約290 KB のメッセージで 10〜25 ms の遅れが約2割のフレームに出る。.NET のクライアントで受信バッファを 4 MB にすると消えた(0.66 ms)。ブラウザー(Chromium)でも 1080p では平均 6〜11 ms(最大 約40 ms)の遅れがあり(480p でもときどき出た)、ブラウザーの設定はサーバーからは変えられない。遅延を最小にしたい場合は、解像度や品質を下げてフレームを小さくする。
- **ブラウザーまでの遅延の大半は、引き続きカメラ側**(約34〜40 ms)。720p ではサーバーの改善分(約2 ms)がそのまま描画までの遅延に表れた。
- **複数クライアント**: エンコードは1回のままで、720p では1台増えるごとの CPU の増加は約0.1 %(全コア比)。

### 分かったこと(Phase W3)

- **顔検出は配信の遅延に影響しない**: 到着→配信可能、受信までの遅延とも、検出の有無で差は誤差の範囲。前処理はエンコードの後に取込スレッドで行い(約0.8 ms)、推論は専用のスレッドで行うため。
- **増えるのは CPU だけ**: 推論 約7.2 ms × 30fps で、1コアの約24 %(全コア比で約1 %)。割当はほぼ増えない(推論1回あたり約21バイト)。
- **顔枠は1フレーム遅れる**: フレームを公開する時点では、まだそのフレームの推論が終わっていないため、直前のフレームの結果を付けている。検出を待ってから公開すると、配信が推論の時間(約8 ms)だけ遅れるので、遅延の小さいほうを選んだ。
- **ワーキングセットは約35 MB 増える**: ONNX Runtime とモデルを起動時に読み込むため(画面から ON/OFF できるように、検出が OFF でも読み込んでいる)。

## 追加の改善

後から次の改善を加えました。最初の2つは FaceViewer と WebStream の両方に効きます。

### フレーム受信の割当をなくす

- MediaFrameReader の FrameArrived を、CsWinRT の投影ではなく COM の vtable で購読するようにしました(`FrameArrivedSubscription`)。ComWrappers で作ったハンドラーを add_FrameArrived に渡し、受け取った IMediaFrameReader から直接フレームを読みます。
- 投影ではイベントのたびに引数のラッパーが作られ、約440 B/フレームの割当になっていました(プローブで計測。直接購読では割当なし)。
- FaceViewer(検出なし)の割当は 118 → 102 KB/s(YUY2 640x480)、113 → 104 KB/s(NV12 1280x720)になりました。WebStream では割当トレースから WinRT のイベント引数が消え、配信経路に残る割当は ASP.NET Core と .NET の内部だけになりました。

### 検出の前処理の SIMD 化

- TensorConverter を、列ごとの座標を先に計算し、4隅の値をスカラーで集めてから AVX2 で8画素ずつ補間・色変換する形にしました。この PC(Ryzen 9 5900X)では gather 命令が遅いので使っていません。
- 計算の順序をスカラー版と同じにしてあり、結果はビット単位で一致します(テストで確認)。

| 構成 | 変更前 | 変更後 |
|:--|--:|--:|
| FaceViewer YUY2 640x480 | 0.93 ms | 0.27 ms |
| FaceViewer NV12 1280x720 | 0.91 ms | 0.29 ms |
| WebStream YUY2 640x480 | 0.77 ms | 0.25 ms |
| WebStream NV12 1280x720 | 0.78 ms | 0.38 ms |
| WebStream NV12 1920x1080 | − | 0.35 ms |

前処理は約1/3になりました。減った時間は1フレームあたり約0.5 ms(1コアの約1.5 %)で、CPU 使用率の差は計測のばらつきに埋もれる程度です。

### MJPEG の表示を1フレーム早める(WebStream)

- Chromium は `multipart/x-mixed-replace` の各パートを、次のパートのヘッダーを受け取った時点で表示します。これまでは「境界 + ヘッダー(Content-Length)+ JPEG」の順に書いていたため、各フレームは次のフレームが届くまで表示されず、1フレーム分(30fps で約33 ms)遅れていました。
- JPEG の直後に、境界と次のパートのヘッダーを書くように変えました。そのため、パートに Content-Length は付きません(次の JPEG の大きさはまだ分からないため)。Content-Length で区切るクライアントでは読めないので、境界(または JPEG の SOI / EOI)で区切ってください。VLC などのプレイヤーは境界で区切るので問題ないはずですが、この PC には入っていないため確認していません。

テスト用のサーバーから2枚を3秒間隔で送り、組み込みブラウザー(Chromium)で表示された時刻を比べました。

| 書き方 | 1枚目 | 2枚目 |
|:--|--:|--:|
| ヘッダー + JPEG(変更前) | 3.0 秒後(2枚目の到着時) | 計測した6秒間は表示されない |
| ヘッダー + JPEG + 境界 | 3.0 秒後 | 計測した6秒間は表示されない |
| JPEG + 境界 + 次のヘッダー(変更後) | 25 ms 後 | 3.0 秒後 |

JPEG の直後に境界だけを書いても、Chromium では変わりません。変更後のサーバーでは、`<img>` を作ってから 31 ms で最初のフレームが表示され、3秒間に89フレーム(約30fps)が描かれました。curl で受け取った3秒分(61フレーム)も、すべてのパートが JPEG の SOI から EOI までそろっていました。

## 動体検知

FaceViewer と WebStream の両方で、映像の中で動いたところを 32x24 のマスで表示します。顔検出と連動させると、動きがない間は検出の間隔を空けて CPU を減らせます(録画や通知はしません)。

### 処理の流れ

```
FrameArrived (取込スレッド、表示用の書き込みやエンコードの後)
  └─ 輝度を 160x120 に縮小(面積平均)
       → 背景(指数移動平均)との差がしきい値を超えた画素を数える
       → 5x5 画素のマスごとに、変化した画素の割合が CellRatio 以上なら「動いたマス」
       → 動いたマスの割合が MinArea 以上なら「動きあり」。背景を BackgroundRate で更新
```

- 縮小の縦方向の足し込みは AVX2 で行います(NV12 は Y 面を16画素ずつ ushort に広げ、YUY2 は ushort として読んで下位バイトを取る)。BGRA は (B + 2G + R) / 4 で近似します。作業領域は最初に確保し、フレームごとの割当はありません。
- 最初のフレームと、ON にした直後・カメラを開き直した後は、背景を作り直します。背景ができるまでの間(`MotionHoldTime`)は「動きあり」として扱います。
- FaceViewer では、動いたマスを 32x24 の WriteableBitmap(1マス = 1画素)に書き、補間なしで映像の範囲に引き伸ばして、半透明のオレンジで重ねます。UI スレッドへの通知は、マスが変わったときだけです。
- WebStream では、クライアントがいるときだけ動かし、結果を WebSocket のヘッダーに入れてビューアーが canvas に描きます。配信の遅延に影響させないようにエンコードの後で処理するので、ヘッダーには直前のフレームの結果が入ります。
- 連動(`Detect:MotionGate`)を有効にすると、最後の動きから `MotionHoldTime` を過ぎた後は、顔検出の前処理を `IdleInterval` ごとにだけ行います。止めはしないので、動かない顔も1秒ごとに検出し直します。

画面では、FaceViewer・ビューアーとも「Motion detection」「Detect only on motion」のチェックボックスで切り替えられ、計測値に Motion(状態と動いたマスの割合)と Motion time が出ます。

### 分かったこと

- **処理は1フレームあたり 0.1〜0.4 ms**: 1080p でも約0.4 ms で、大半は縮小(縦方向の足し込み)の時間。差分と判定は 160x120 で行うので、解像度によらない。
- **配信・表示の遅延と割当には影響しない**: 表示用の書き込みやエンコードの後に取込スレッドで処理するため。到着→配信可能、受信、Display latency とも差は誤差の範囲で、割当も増えない。
- **連動の効果は大きい**: 動きのない場面では、顔検出が 30 → 1 fps になり、CPU は1コアの約31〜36 % から約7〜8 % に減った。推論(約7〜8 ms × 30fps)がほぼなくなるため。
- **人がいる場面では、連動の効果は出にくい**: 小さな動きでも「動きあり」になり、その後 `MotionHoldTime` の間は検出を続けるため。効くのは、誰もいない・動かない時間が長い場面。
- **WebStream の動きの結果は1フレーム遅れる**: 顔枠と同じく、配信の遅延を増やさないことを優先した。

## 検知範囲

動体検知と顔検出を、指定した範囲だけで行います(テレビや窓の外、揺れるカーテンなど、関係のない動きや顔を除くため)。範囲は動体検知と同じ 32x24 のマスで持ち、両方の検出で共有します。

- 動体検知: 範囲外のマスは、動いても数えません。動いたマスの割合(`Motion:MinArea` と計測値の Motion の %)は、範囲のマス数に対する割合です。範囲が画面全体なら、これまでと同じ結果になります。背景は範囲外も更新し続けるので、範囲を変えても作り直しません。
- 顔検出: 顔枠の中心が範囲外にある顔を、結果から除きます(表示にも WebSocket のヘッダーにも出ません)。推論の回数は変わりません。
- 連動: 範囲内の動きだけで判断します。範囲外が動いていても、顔検出は間隔を空けたままです。

### 操作

- FaceViewer: 「Edit area」をオンにすると、映像にマスの線が出て、範囲外が暗くなります。ドラッグすると、押したマスから今のマスまでの長方形を塗ります。押したマスが範囲内なら外し、範囲外なら加えます(クリックだけなら1マス)。塗った範囲はすぐ判定に反映し、離したときにファイルへ保存します。「Reset area」で画面全体に戻ります。
- ビューアー(WebSocket 表示のとき): 同じ操作を canvas で行います。ドラッグ中はビューアーの表示だけが変わり、離したときに `PUT /api/area` でサーバーに反映・保存します。ほかのビューアーは、`/api/status` の `areaVersion` が変わると範囲を取り直します(1〜2秒以内)。
- 範囲が画面全体でないときは、範囲外を薄く暗く表示します(編集中は少し濃く)。

全体から小さい範囲を作るときは、画面全体を外すドラッグと、見たい場所を加えるドラッグの2回で済みます。

### 保存

範囲はアプリごとの JSON ファイル(`Area:Path`)に保存し、起動時に読み込みます。`appsettings.json` は画面から書き換えないので、別のファイルにしています。既定の場所は `%LOCALAPPDATA%` の下なので、Debug と Release で共通です。2つのアプリで同じパスを指定すれば、範囲を共有できます(読み込むのは起動時だけです)。

```json
{
  "columns": 32,
  "rows": 24,
  "cells": [
    "00000000000000000000000000000000",
    "00000000111111111111111100000000",
    ...
  ]
}
```

- `cells` は上の行から 24 行、1マス1文字(`1`: 範囲内、`0`: 範囲外)なので、手でも直せます(コメントと末尾のカンマも書けます)。
- ファイルがなければ画面全体です。形式が違うときは、警告をログに出して画面全体で動きます。
- 一時ファイルに書いてから置き換えるので、書き込みの途中で止まってもファイルは壊れません。
- 解像度やフォーマットを変えても、同じ範囲を使います(4:3 と 16:9 ではカメラが映す範囲が変わるので、少しずれることがあります)。

### 計測結果(Release ビルド、YUY2 640x480)

動体検知の処理時間(1フレームあたりの平均)

| アプリ | 範囲 | 処理時間 |
|:--|:--|--:|
| FaceViewer(顔検出なし、交互に2回ずつ) | 全体 | 0.170 / 0.127 ms |
| FaceViewer(顔検出なし、交互に2回ずつ) | 上半分を外す | 0.150 / 0.130 ms |
| WebStream | 全体 | 0.180 ms |
| WebStream | 左上の一帯(208 マス) | 0.175 ms |

範囲の処理は、96 バイトのマスクの AND とビットの数え上げだけです。

連動の効果(実際の場面、WebStream)

動いたマスを40秒集計し(マスごとに動いた回数だけを数える)、一度も動かなかった上の3行と左上の一帯(行 3〜10、列 0〜13、計 208 マス)を範囲にしました。

| 範囲 | 連動 | 顔検出 | 顔の数 | 動きあり | CPU(1コアあたり) |
|:--|:--|--:|--:|--:|--:|
| 全体 | なし | 29.8 fps | 1.00 | 6/7 | 36.9 % |
| 左上 | なし | 29.9 fps | 0.00 | 1/7 | 38.7 % |
| 全体 | あり | 28.8 fps | 1.00 | 7/7 | 38.7 % |
| 左上 | あり | 1.0 fps | 0.00 | 1/7 | 7.7 % |

「動きあり」は5秒ごとの値のうち動きありだった数で、左上の 1/7 は起動直後(背景ができるまでは動きありとして扱う)の分です。配信(到着→配信可能 0.95〜1.06 ms、取込→受信 35.2〜35.5 ms)と割当(34〜37 KB/s)は、どの組み合わせでも同じでした。

FaceViewer でも同じ範囲で2回比べましたが、計測中は範囲の中でも人の動きがあり(動いたマスの割合 3.5〜5.6 %)、連動時の顔検出は 18.4〜23.9 fps でした。範囲の中が静かになった区間では 1.0 fps に下がりました。

割当(FaceViewer、顔検出なし): 動体検知なし 107 / 128 KB/s、動きのない条件(`Motion:Threshold=255`)で動体検知あり 112 KB/s で、範囲の処理による増加はありませんでした。

### 分かったこと

- **範囲は処理時間にも割当にも影響しない**: マスの判定の後にマスクを AND するだけなので、差は誤差の範囲。
- **関係のない動きを範囲外にすると、連動が効く**: 人が動いている場所を外すと、顔検出が 30 → 1 fps になり、WebStream の CPU は1コアの約39 % から約8 % に減った。画面のどこかが動いていることが多い場面でも、見たい場所だけに絞れば連動の効果が出る。
- **効果は範囲の中の動きしだい**: 範囲の中に人が入れば「動きあり」になり、検出は続く(FaceViewer の計測)。人の出入りを見張りたい場所(入口など)を範囲にするのが向いている。
- **顔は枠の中心で判定する**: 範囲の境目にかかった顔は、中心がどちら側にあるかで出たり消えたりする。
